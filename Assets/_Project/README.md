# TDS — тестовое задание

Top-down shooter на Unity. Весь код проекта — в `_Project/Code`.

## Стек

- **VContainer** — DI и жизненный цикл (entry points: `IStartable` / `ITickable` / `IDisposable`)
- **UniTask** — асинхронность (загрузка, экраны)
- **R3** — реактивность (здоровье, текущее оружие → UI)
- **uPools** — пулинг (враги, снаряды, HP-бары)

## Архитектура

Подход — **data-oriented / псевдо-ECS**: вместо OOP-иерархий сущность = «данные + реестр», а логика живёт в системах, которые тикаются над реестрами. ООП/SOLID не догматизируется.

### Ключевые паттерны

- **Полиморфные SO-конфиги + процессоры рядом.** Конфиг (`ScriptableObject`) и его процессор лежат в одном файле. Диспетчеризация по типу через `Dictionary<Type, IProcessor>` (оружие, способности, поведение врагов, модификаторы урона, спавн арены, тултипы). Новый вид = новый файл, без правок существующих.
- **Конфиг / runtime / view разделены.** Конфиг неизменен (SO), runtime-данные мутабельны (`*RuntimeData`, `*Context`), view — пассивный `MonoBehaviour`. Контексты переиспользуются между вызовами (ноль аллокаций на выстрел/каст).
- **Фабрики.** `PlayerFactory`, `EnemyFactory`, `ProjectileFactory` собирают сущность целиком и регистрируют её во всех реестрах (`*Registry`, `CombatEntityRegistry`, `HittableRegistry`).
- **Реестры + системы.** Системы итерируют живые списки реестров с гардом `IsAlive` (без снапшотов).
- **Отложенный деспавн.** `DespawnSystem` копит запросы и выполняет структурные изменения одной фазой в конце кадра.
- **Событийная развязка.** `CombatDeathStream`, `ArenaResultStream` — нижний слой публикует факт, доменные обработчики решают что делать (смерть → деспавн врага / экран поражения). Combat не знает про врагов и UI.
- **Пространственные запросы.** `HitQueryService` — единая точка overlap-проверок по XZ (живой список `HittableRegistry`), без физических коллайдеров.

### Поток приложения

```
Bootstrap → Core → GameStateMachine → GameplayState
                                         ├─ загрузка конфигов (Addressables)
                                         ├─ загрузка сцены
                                         └─ GameplayLifetimeScope → GameplayRunner
```

`GameplayRunner` — **явный оркестратор**: владеет порядком инициализации (создать игрока → поднять HUD) и порядком тика (движение → камера → бой → враги → снаряды → деспавн). Рестарт арены = повторный вход в `GameplayState` (полная пересборка scope).

### Бой

Урон проходит через пайплайн модификаторов: атакующие (крит, % урона) и защитные (броня, уклонение) — каждый отдельный SO + процессор. `DamageApplicationService` — единственная точка применения урона, публикует смерть в `CombatDeathStream`.

### UI (MVP)

- Пассивные `View` + медиаторы, владеющие подписками. `HudController` централизует инициализацию HUD.
- `ScreenManager` (`ShowAsync` / `ShowAndAwaitAsync` с аргументами) + `PauseManager` — экраны Victory/Defeat ставят игру на паузу.
- Динамические тултипы через процессоры (данные из SO-конфигов), кастомный прицел, реакция курсора на блокирующий UI.
- Все спавнящиеся под персистентный канвас вьюшки чистятся через `IDisposable` при разрушении scope.

## Структура

```
Code/
  Application/      Bootstrap, Core, стейт-машина, загрузочный экран
  Infrastructure/   ConfigService (Addressables), SceneLoading, камеры
  Gameplay/
    Combat/         урон, статы, модификаторы, реестр сущностей
    HitDetection/   пространственные запросы (Hittable)
    Player/         фабрика, движение/поворот, combat-entity, HUD
    Enemies/        фабрика, реестр, поведение (движение/оружие), HP-бары
    Weapons/        инвентарь, оружие (мили/дальнобой), HUD
    Abilities/      слоты, способности (деш, AoE), HUD
    Projectiles/    фабрика, движение, попадания
    Arena/          триггер, расписание спавна, условие победы
    UI/             ScreenManager, тултипы, курсор, виджеты
    Pause/          PauseManager
```
